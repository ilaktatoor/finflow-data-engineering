# Solutions · 07 ELT pipelines

## Exercises
1. `10_elt_check_new_transactions.sql` reads only `load_seq > elt_watermark.last_load_seq`, and
   `load_raw` inserted nothing new (`ON CONFLICT (batch_id, record_position) DO NOTHING`).
2. Reconciliation reports the days where the extra rule rejected rows in one path only. Fixing
   means adding the twin rule to the other path.
3. Stage `loan_payments` raw from Bronze like `load_raw`, type with regex-guarded casts, check
   `principal + interest = amount` in SQL, upsert into `elt_loan_payments`, and compare
   `COUNT(*)`, `SUM(amount)` per month with `fact_loan_payments`.
4. `(amount * rate + 500000) / 1000000` becomes a DOUBLE division: inserting into the BIGINT
   column rounds instead of truncating, so some conversions differ by one cent from the ETL and
   the reconciliation reports mismatched days (and money went through floats).

## Interview answers
1. ETL for complex validation, sensitive raw data, or expensive warehouse compute; ELT when the
   warehouse is the scalable, cheap engine and SQL ownership by analysts matters. Usually both.
2. Track a high-water mark on an ever-increasing load column, process only newer rows, upsert,
   and advance the mark in the same transaction.
3. Independent implementations, compared on counts and sums per partition (FULL OUTER JOIN +
   `IS DISTINCT FROM`), automated in tests.
4. Dependency graph between models, tests, documentation, incremental materialisations,
   environments — the structure FinFlow's numbered SQL files approximate by hand.
