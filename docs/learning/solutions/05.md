# Solutions · 05 Data modelling

## Exercises
1. Hash only `segment, city, state` (and names) in `SCD2_ATTRIBUTES`; before the SCD2 statements
   add `UPDATE dim_customer SET email = s.email FROM stg_customers s WHERE dim_customer.customer_id = s.customer_id;`
   (all versions — "type 1 on a type 2 dimension", sometimes called SCD6-style handling).
2. Create `dim_channel(channel_key, code)`, seed it in `01_schema.sql`, add `channel_key` to
   `fact_transactions` with an FK, join `dim_channel ON code = s.channel` in the load, and
   update marts that group by channel.
3. Facts of customers with several versions now match all of them. Measured on DuckDB, the
   load does **not** fail on its own: `ON CONFLICT` keeps one of the candidate rows, counts and
   amounts still reconcile, and facts silently point at the wrong version (84 wrong links after
   two incremental days and a re-run of the historical batch). This is why `_reconcile_facts`
   also runs a point-in-time check: with it, the load raises
   `ReconciliationError: fact_transactions: N rows point at a customer version not valid at event time`
   and rolls back. (PostgreSQL documents a different reaction: an `ON CONFLICT DO UPDATE` that
   would update the same row twice in one statement is an error.) The test
   `test_point_in_time_guard_catches_wrong_customer_version` keeps the guard honest.
4. Grain: one row per account per day. Measures: closing balance (semi-additive: sum across
   accounts, never across days; use last/average over time), daily inflow/outflow (additive).

## Interview answers
1. What one fact row represents; it defines which dimensions apply and prevents double counting.
2. SCD1 overwrite (corrections, no history needed); SCD2 new row per change (history matters);
   SCD3 previous-value column (one level of history, rare).
3. Stable across source changes, enable SCD2 versions, cheaper joins, protect against key reuse.
4. Snowflake normalises dimensions into sub-dimensions; star keeps them flat — simpler, faster joins.
5. Quarantine and replay (FinFlow), or load against an "unknown/inferred member" and update it later.
