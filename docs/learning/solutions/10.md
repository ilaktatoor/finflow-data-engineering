# Solutions · 10 Airflow orchestration

## Exercises
1. ```python
   def record_failure(context):
       Path("/opt/finflow/data/reports").mkdir(parents=True, exist_ok=True)
       with open("/opt/finflow/data/reports/airflow_failures.log", "a") as f:
           f.write(f"{context['ti'].dag_id} {context['ti'].task_id} {context['run_id']}\n")
   DEFAULT_ARGS["on_failure_callback"] = record_failure
   ```
2. Add a task listing pending batch ids (`finflow status` or a small new CLI command printing
   JSON), then `finflow_task.partial(...).expand(bash_command=[...])` or a `@task` returning the
   list and a mapped BashOperator.
3. Every parse (every ~30 s per file) would import pandas/pyarrow and read storage; inside the
   Airflow interpreter `finflow` is not even installed (it lives in its own venv), so the import
   fails and the DAG disappears with an import error.
4. Use `{{ ds }}` to compute the batch id; backfills and reruns of a logical date then process
   the same batch deterministically instead of generating a new one.

## Interview answers
1. Structure only: DAG definition, operators, dependencies, parameters. No data access or heavy
   imports at top level; logic in packages or containers.
2. Through external storage; XCom only for small references.
3. Clear that task instance (with or without downstream) for the logical date, or
   `airflow tasks clear`.
4. Schedules for time-based work, sensors for waiting on external state (deferrable when
   possible), datasets/assets for data-driven triggering between DAGs.
