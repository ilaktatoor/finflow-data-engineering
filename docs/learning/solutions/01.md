# Solutions · 01 Python for data engineering

## Exercises
1. In `configure_logging`, read `os.environ.get("FINFLOW_LOG_FORMAT", "json")` and pick
   `logging.Formatter("%(asctime)s %(levelname)s %(name)s %(message)s")` for `text`.
   Better: add `log_format` to `Settings` so it is configured like everything else.
2. In the `except BaseException as exc:` branch of `track_step`, keep `status, error` and add
   `log.error("step failed", extra={"step": step, "exc_type": type(exc).__name__})` before `raise`.
3. With `return` instead of `raise`, the context manager *swallows* the exception: `run_etl`
   continues and sets the batch to `TRANSFORMED`/`LOADED` although the load rolled back. The
   orchestrator sees success and the data is missing — the worst failure mode.

## Interview answers
1. Generate a run id at the start, bind it (and the batch id) to a logging context
   (`contextvars`), emit structured logs, and store the same ids in the data (lineage columns)
   and in execution metadata tables.
2. The context manager guarantees rollback on every exit path, including exceptions raised
   by code you did not write, and makes the transaction boundary visible in the code.
3. Worth it at I/O boundaries you want to fake in tests (HTTP clients, clocks, storage).
   Ceremony when it wraps pure functions or has a single implementation forever.
4. Success, failure that may succeed on retry, and failure that will not (bad data). FinFlow
   uses 0, 1 and 2 so Airflow can treat them differently.
