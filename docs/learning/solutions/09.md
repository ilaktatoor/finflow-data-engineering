# Solutions · 09 Incremental processing

## Exercises
1. `seed` writes both days' rows; `etl` runs batch 1 then batch 2. Batch 1 extracts
   `(previous watermark, day-1 end]`: the 3 customers changed on day 1. Batch 2 extracts the 3
   changed on day 2. A customer changed on *both* days has only its day-2 state in the database,
   so batch 1 does not see it (the row's `updated_at` moved) — the classic limit of
   state-based extraction versus change capture.
2. Use `lower = watermark - timedelta(hours=1)` in `OperationalSource.extract`; overlapping rows
   are re-extracted; SCD2 hashes and upserts make them no-ops. A services test that back-dates a
   row by 30 minutes after the watermark proves it.
3. A failed load leaves the watermark advanced: the retry extracts *after* the window, and the
   window's changes are never loaded.
4. The batch guard `WHERE EXCLUDED.batch_id >= fact_transactions.batch_id` (and `updated_at` for
   SCD1 dimensions).

## Interview answers
1. A monotonic column (`updated_at`, id) and a stored high-water mark; read
   `(watermark, now_cutoff]`, upsert, advance in the same transaction as the load.
2. Back-dated or clock-skewed writes are missed, deletes are invisible, intermediate states are lost.
3. Facts: accept, flag, upsert onto their event date. Dimensions: quarantine and replay, or
   inferred members updated later.
4. When data is small, when logic changes often, or when correctness is worth more than cost.
