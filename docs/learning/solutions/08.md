# Solutions · 08 Data quality

## Exercises
1. Add a dataframe check in `_business_checks("transactions")`:
   `pa.Check(lambda df: (df["transaction_type"] != "FEE") | (df["amount_minor"] <= 50_000), name="fee_max_amount", ignore_na=False)`,
   a failing test first (a FEE of `600.00` expecting `business:fee_max_amount`), the twin rule in
   the ELT SQL, then run the suite.
2. In `quality.evaluate`, after the per-rule rows, compare
   `result.rule_failures["schema_mismatch"] / n` with a new `max_schema_mismatch_rate` in
   `[quality]` and append to `critical`.
3. `transfer_requires_counterparty`, `purchase_requires_merchant` and
   `payment_components_reconcile` cases fail: with `ignore_na=True`, Pandera drops rows that
   contain a null *before* running a dataframe-level check — exactly the rows these rules exist
   to catch.
4. In `evaluate`, when `stale` is true, also append to `critical` (or behind a config flag).

## Interview answers
1. Completeness (required not null), validity (allowed values, formats), uniqueness (no
   duplicate keys), consistency (cross-field rules, owner matches), referential integrity (FK
   exists), freshness (newest event within N hours), accuracy (matches an external truth).
2. Quarantine single bad records; fail the batch when the bad share means the source is broken
   or loading would mislead consumers.
3. Contract checks on presence/absence of fields (`schema_mismatch`), type parse failures,
   and alerting when a rule's failure rate jumps.
4. An explicit, versioned agreement between producer and consumer on fields, types, semantics
   and quality — `contracts.py` + `source-contracts.md` here.
