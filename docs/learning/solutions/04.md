# Solutions · 04 Advanced SQL

## Exercises
1. ```sql
   WITH daily AS (SELECT full_date, completed_mxn_minor FROM mart_daily_transactions)
   SELECT full_date, completed_mxn_minor,
          completed_mxn_minor - LAG(completed_mxn_minor) OVER (ORDER BY full_date) AS change_minor,
          ROUND(100.0 * (completed_mxn_minor - LAG(completed_mxn_minor) OVER (ORDER BY full_date))
                / NULLIF(LAG(completed_mxn_minor) OVER (ORDER BY full_date), 0), 2) AS change_pct
   FROM daily ORDER BY full_date;
   ```
2. DuckDB: `... FROM per_customer QUALIFY ROW_NUMBER() OVER (PARTITION BY segment ORDER BY completed_minor DESC, customer_id) <= 3`.
   PostgreSQL has no `QUALIFY`, so the shared SQL uses an outer query.
3. ```sql
   WITH RECURSIVE days(d) AS (
       SELECT CAST(MIN(event_ts) AS DATE) FROM fact_transactions
       UNION ALL
       SELECT CAST(d + INTERVAL '1 day' AS DATE) FROM days
       WHERE d < (SELECT CAST(MAX(event_ts) AS DATE) FROM fact_transactions))
   SELECT d FROM days;
   ```
4. `RANGE` with an offset needs a numeric/date-compatible order key; PostgreSQL requires an
   `INTERVAL` offset for dates (`RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW`),
   and DuckDB likewise. With an interval, `RANGE` is calendar-correct even without
   densification — the trade-off versus `ROWS`.
5. Change `ORDER BY load_seq DESC` to `ASC`: for status corrections the kept copy becomes the
   old PENDING one — the "first copy" rule is wrong for corrections.

## Interview answers
1. ROW_NUMBER: unique 1..n; RANK: ties share a rank, gaps follow; DENSE_RANK: ties share, no gaps.
2. `ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) = 1` in an outer query.
3. ROWS counts physical rows; RANGE includes peers with equal order values or an offset range of values.
4. When reads are frequent, the query is expensive, staleness is acceptable, and the engine
   supports incremental or concurrent refresh; a rebuilt table is more portable.
5. Estimated vs actual rows (bad estimates explain bad plans), the most expensive node, scan
   types, sorts/hashes spilling to disk.
