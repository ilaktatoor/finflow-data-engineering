# Solutions · 11 Data lake and Parquet

## Exercises
1. With the filter the plan shows the file list reduced to one partition (DuckDB prints the
   pruned file count / filter on `txn_date`); without it every file is scanned.
2. Files multiply by the number of channels (6×) with ~10 rows each: per-file overhead
   dominates. Not worth it at this size; partition keys should produce files of tens to
   hundreds of MB.
3. `BronzeConflictError: Checksum mismatch for ...: Bronze object was modified.`
4. Read the partition's files, write one new file under a temporary name, verify row counts,
   then delete the old files. Without a table format this is not atomic: readers can see
   duplicates or gaps mid-operation, which is the problem Iceberg/Delta solve.

## Interview answers
1. Bronze: raw as received, immutable. Silver: cleaned, typed, deduplicated, conformed.
   Gold: business models (star schemas, marts).
2. Types, compression, column pruning, statistics for predicate pushdown, splittable files.
3. Skipping partitions using the filter; choose low-to-moderate cardinality keys that queries
   filter on (usually dates).
4. Atomic commits, schema evolution, time travel, concurrent writers, hidden partitioning, compaction.
