# Solutions · 13 Performance optimisation

## Exercises
1. Expect vectorisation and categoricals to keep their advantage; Parquet's read time to get
   closer to or beat CSV; chunking still neutral (10k rows still fit easily in memory).
   Measure and record — do not assume.
2. ```python
   con = duckdb.connect(); con.register("s", df)
   median_ms(lambda: con.execute("SELECT txn_date, SUM(amount_mxn_minor) FROM s GROUP BY 1").df())
   median_ms(lambda: df.groupby("txn_date")["amount_mxn_minor"].sum())
   ```
3. With the index (and enough rows, or `SET enable_seqscan = off` to force it for learning),
   the Sort node can be replaced by an Index Scan delivering rows in `(account_key, event_ts)`
   order. At 2k rows the planner may keep the sort — cheaper.
4. A fast wrong result looks like success; benchmarks without equivalence checks reward bugs.

## Interview answers
1. Measure end to end, find the dominant step (logs, step metrics, profilers), then optimise
   that step; re-measure.
2. Wins on large data with column/row-group pruning and when types matter; not on tiny files.
3. Useless on low selectivity or tiny tables; harmful on write-heavy tables.
4. Proper dtypes (category, smaller ints, Arrow strings), reading only needed columns, chunks.
